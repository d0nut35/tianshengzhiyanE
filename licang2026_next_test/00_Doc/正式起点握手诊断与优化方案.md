# 正式起点握手诊断与优化方案

2026-10-09。用户反馈自己编译下载红方正式程序后起点不动，无线偶尔也要复位；尚无本次F7/Nano同期日志，不能确认现场根因。本轮已补正式启动日志并验证原逻辑；下面的握手重试优化是待确认方案，尚未改变故障策略。

## 当前实现及检查结论

- STM32在WAIT_HOME/WAIT_CHASSIS_READY每秒主动发送MODEL_QUERY，Nano每次收到查询后回复LOADING/READY/ERROR及原查询序号，不依赖上电一次性广播。协议上支持先开Nano、等待模型就绪后再给STM32供电，不存在仅因漏过一次模型就绪广播而无法握手的问题。
- 起点动作10匹配完成回报、底盘MISSION_READY及本次查询模型READY都收到，颜色有效且正式转盘启动检查已通过，才回MISSION_READY给底盘，进入READY等待4秒再发GO_PLATFORM。模型加载和上电动作10等待仍不设总截止时间。
- 正式在动作10完成后额外执行转盘OPTIONS检查（EMM固件、closed_loop），无线起点门禁没有这一检查，不能仅凭无线能READY就推定正式转盘初始化通过。
- 无回复超时会继续查询；提交繁忙/队列等失败也回到空闲等待下次查询。收到运输IO错误、CRC/帧长度/类型等解码失败或序号不匹配，则当前代码直接FAULT VISION并请求停车；有效MODEL_ERROR也停车。这种单次无效握手帧使起点永久故障的现有行为已由主机测试复现，可能解释复位后恢复，但不证明实机根因就是该项。
- Nano缺少--block-engine、模型文件/环境失败或运行了错误服务目录，会回有效MODEL_ERROR；不通过重试策略掩盖这些明确故障。Nano地址172.20.10.2本轮SSH连接超时，现场服务/日志未直接读取。

## 已添加的正式启动日志

复用MISSION_DEPOT_TRACE_ENABLED，正式0/日志1时从USART1输出；回调不打印，日志不参与判定，不新增无线命令或改变通信协议。起点汇总最多每秒一行，查询/回复及状态转场按实际事件输出。

| 日志 | 用途 |
| --- | --- |
| [BOOT] FORMAL SIDE=RED/BLUE ... POLL=1000MS | 确认当前是正式日志版、构建颜色及查询周期 |
| [BOOT] WAIT STATE=... ARM10=... CHASSIS=... MODEL=... V=... BUSY=... PENDING=... LAST=... | 找出起点尚未满足的就绪项或未消费的UART事务 |
| [BOOT] MODEL QUERY SEQ=... SUBMIT=... | 本次查询序号、是否实际提交成功 |
| [BOOT] MODEL RX IO=... LEN=... TYPE=... SEQ=... EXPECT=... | 区分无回复、半包、其它消息或旧查询回复 |
| [BOOT] MODEL DECODE=... | 帧校验/载荷校验结果 |
| [BOOT] MODEL STATE=... REASON=... | Nano模型加载中、已就绪或明确错误 |
| [BOOT] ZDT OPTIONS QUERY/RX/CLOSED/FW | 正式额外的转盘查询、等待、回复类型及闭环/固件条件 |
| [BOOT] GATE READY ... START_IN=4000MS | 所有门禁通过，已进入自动启动倒计时 |
| [BOOT] AUTO START ... GO_PLATFORM ID=... | 已进入正式出发分支；与后续底盘回报匹配 |

STATE=1等动作10，STATE=2等底盘/Nano就绪，STATE=3为4秒倒计时，STATE=4等圆盘到位。ARM10/CHASSIS/MODEL为1才表示相应条件通过。V=5为模型查询事务，V=0为空闲。LAST高位为机械臂回报事件、低8位为动作组；动作10完成仍以[M] ARM DONE及实际状态转场判断。

SUBMIT/IO/DECODE沿用nano_vision_status_t：0成功、2长度、3版本、4类型、5CRC、6值、7序号、8超时、9忙、10队列满、11IO。MODEL STATE：0加载、1就绪、2错误；REASON=10为模型错误。MODEL_STATE消息TYPE=134（0x86）。序号不匹配时DECODE可能为0，但SEQ与EXPECT不同，仍按原策略进入FAULT=4。ZDT CLOSED需1，FW需1（EMM），否则FAULT=5（STORAGE）；ZDT IO是独立转盘状态枚举，不能套Nano IO编号。

若没有任何[M]/[BOOT]标题，先核对是否烧录正式日志版及USART1连接/波特率115200；也可能在任务运行前初始化失败，不能据此认定是Nano握手。如果出现GATE READY而没有AUTO START，核对是否4秒内STOP或出现后续FAULT；出现AUTO START但车不走时优先看底盘握手/GO_PLATFORM处理，不能继续归因于模型未就绪。

## 待确认的最小优化方案

1. 继续由STM32每秒查询，只有匹配本次序号、校验完整的MODEL_READY才置位模型就绪；不取消模型、动作10、底盘和转盘检查。
2. 仅在起点MODEL_QUERYING分支，把半包/坏CRC/非模型帧/旧序号归为本次握手无效：消费当前回调邮箱、保持MODEL未就绪，等下个间隔以新序号重新查询。连续失败需要明确计数/提示；不立刻把一次串口噪声锁存为永久FAULT，也不直接放行运动。
3. 起点提交繁忙和超时继续原重试；运输IO错误先依据日志区分是否瞬时UART错误，再决定是否同样允许起点重试。校验正确且序号匹配的MODEL_ERROR保留故障停车；STOP后忽略迟到READY，不恢复任务。
4. 不将这种起点容错扩散到开赛后的球事件、积木数字、ACK或C100会话，不放宽帧龄/动作回报。若日志证明实际卡在转盘OPTIONS，另修复该环节；本次不跳过转盘检查或猜配置。
5. 修改后用实际生产分支验证“无效帧→未放行→下次新查询READY→三项齐备→4秒出发”，并覆盖长时间LOADING、明确MODEL_ERROR、连续失败、STOP/迟到回复及正式/无线一致性，最后现场重复断电上电验证。

先采一轮完整F7启动日志，并同步Nano的BLOCK MODEL READY或MODEL ERROR日志，按SEQ/IO/DECODE及门禁项决定实施范围。本方案尚未接入运行代码，不能宣称已解决现场启动故障。
